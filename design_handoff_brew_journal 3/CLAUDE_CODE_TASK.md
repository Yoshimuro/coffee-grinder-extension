# TASK для Claude Code: Brew Journal → Android APK (local-first)

Прочитай `README.md` (полная спецификация) и открой `Brew Journal offline.html` в браузере как эталон (один файл, работает с диска). Реализуй **вариант C домашнего экрана** (переключатель A/B/C над рамкой телефона — выбери C, язык RU).

## Цель
Полноценный APK: local-first, полностью офлайн, без аккаунтов и сети. В перспективе тот же кодбейс станет PWA — закладывай это сразу.

## Стек (рекомендация — можно оспорить с аргументами)
- SPA: React + Vite (или Preact), TypeScript.
- Данные: IndexedDB через Dexie. Схема — раздел «Модель данных» README.
- Обёртка: **Capacitor 6** → APK. Плагины: Camera (полка), Filesystem + Share (экспорт/импорт JSON, QR), @capacitor-community/keep-awake (таймер), LocalNotifications («оценка ждёт»), @capacitor-community/speech-recognition (голос; при недоступности офлайн — молча деградировать до клавиатуры, без баннеров). Все плагины кроссплатформенные: `npx cap add ios` позже даст Xcode-проект из того же кода — держи web-слой без Android-специфики.
- PWA-готовность: manifest, service worker (Workbox), всё работает в браузере без Capacitor.

## Что переносить как есть
- `data.js`: словарь колеса (WHEEL/DESC), строки RU/EN (STR), TRAITS девайсов, GRINDER_DB, формулы конвертации (µm-модель, ±12 µm диапазон), фазы свежести. Портируй в TS-модули, сохрани id дескрипторов.
- Логика из класса `Component` в `Brew Journal.dc.html`: stagesFor (генерация стадий по форме кофе и режиму), таймер с записью фактических длительностей и паузами, калибровка (offset в шагах своей кофемолки), devSvg (генеративный чертёж девайса), wheelSvg (геометрия колеса, arcPath), сравнение с подсветкой отличий.
- **База кофемолок**: в проде заменить GRINDER_DB на базу моего Chrome-плагина (134 шт) — я подключу её отдельно; сделай модуль-адаптер с интерфейсом `{id, name, short, step, zero, dp}`.

Дом (вариант C) · Конвертер (база → своя, калибровка) · Полка + карточка пачки (фото столбцом, мин. 2) + добавление · Девайсы + конструктор с живым чертежом · Сетап заваривания (форма кофе определяет поля; + зерно/+ девайс инлайн) · Таймер ×4 (перколяция/иммерсия/гибрид с клапаном/дрип) с ПАУЗОЙ · Оценка позже · Диагностика (4 шкалы, вход в колесо, голос) · Колесо (3 уровня, память, интенсивность) · Журнал (фильтры, сравнение) · Деталь записи (+QR, повторить) · Настройки (кофемолки с подтверждением удаления, экспорт/импорт).

## Жёсткие требования
- Ни одного сетевого запроса (проверяется). JetBrains Mono бандлится локально в APK.
- Dark-only; tabular-nums на всех цифрах; тач-таргеты ≥48dp; safe area; явная кнопка «назад» на вложенных экранах; уровни колеса — тапом, не жестами.
- Тон копирайта: плоские глаголы, без похвалы, без извинений. Никакой геймификации.
- Токены палитры/типографики — из README, точно.

## Хранение и бюджет (цель: < 200 МБ за годы использования)
- Текстовые данные ничтожны: запись журнала ~1 КБ JSON → 1000 заварок/год ≈ 1 МБ. Словарь колеса + база кофемолок < 100 КБ. Хранить в Dexie как есть, без сжатия.
- **Весь риск — фото пачек** (сырой снимок с камеры 3–5 МБ). Обязательно сжимать на входе: `Camera.getPhoto({ quality: 80, width: 2048 })` (даунскейл делает нативный слой) → итог 200–400 КБ; мелкий шрифт этикетки на 2048px читается. ~150 фото/год ≈ 40–50 МБ/год.
- Фото — **файлами** через Filesystem (Directory.Data), в Dexie только пути + миниатюра ~15 КБ (256px, для полки). Никакого base64 в БД (+33% и раздувание IndexedDB).
- Экспорт базы: JSON + папка фото одним zip (plugin community/zip или JSZip); импорт — обратная распаковка.
- Capacitor сам ничего не сжимает — это ответственность кода на входе. Квоты браузера в APK не действуют (нативное app-хранилище).

## Definition of Done
1. `npx cap run android` собирает и ставит APK на устройство.
2. В авиарежиме: полный цикл — добавить пачку фотографией → заварить с таймером и паузой → оценить (шкалы + колесо + голосовая заметка или клавиатура) → увидеть в журнале → сравнить два заваривания → экспортировать JSON.
3. Удаление приложения и импорт JSON восстанавливает базу.
4. Экран таймера не гаснет; после заваривания приходит локальное уведомление.
5. Пиксельная сверка ключевых экранов с прототипом (эталон — HTML).

## Порядок работы (для агентской системы)
1. Каркас: Vite + TS + роутер + Dexie-схема + токены → пустые экраны с навигацией.
2. Ядро: порт data.js + конвертер + stagesFor + таймер (чистые функции, unit-тесты на конвертацию/стадии/паузы).
3. Экраны по списку выше, сверяясь с эталоном.
4. Колесо (SVG, анимация приближения, память) — отдельным этапом, это signature.
5. Capacitor: плагины, уведомления, keep-awake, камера, экспорт/импорт.
6. Сборка APK, прогон DoD.
