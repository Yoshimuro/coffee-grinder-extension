# Brew Journal — проектная спека

Дата: 2026-08-02. Статус: утверждена (решения ниже согласованы явно).
Первоисточники: `design_handoff_brew_journal 3/README.md` (спека дизайна и поведения), `Brew Journal offline.html` (пиксельный эталон), `CLAUDE_CODE_TASK.md` (цель и DoD), `handbook/` (процесс, адаптирован).

## 1. Цель и рамки

Local-first приложение для спешелти-кофе: конвертер помола → журнал заваривания с таймером → полка зерна → конструктор девайсов → двухшаговая оценка (диагностика + колесо вкусов). Android APK через Capacitor сейчас, тот же кодбейс — PWA потом.

Жёсткие рамки (не проектировать): ни одного сетевого запроса, без аккаунтов, платежей, соцфич, BT, ИИ. Шаринг — только файл или QR. JetBrains Mono бандлится, тач-таргеты ≥48dp, углы прямые, акцентный цвет только на колесе и фото. ~~Dark-only~~ — снято в BJ-9 (D-13): тем две, тёмная остаётся умолчанием, светлая выведена из неё по контрасту; остальные рамки в силе.

## 2. Утверждённые решения

| ID | Решение |
|---|---|
| D-1 | **Движок конвертации = ядро расширения** (`src/core`): linear + anchors-калибровки, снэппинг к реальным засечкам, полоса неопределённости по confidence (5/12/25%, квадратура). Фиксированные ±12 µm и упрощённый адаптер `{id,name,short,step,zero,dp}` из прототипа не используются. Поверх ядра — калибровочный offset из прототипа (шаги своей молки, применяется к center/lo/hi после инверсии). UI конвертера — по дизайну. |

| D-3 | **README побеждает прототип.** README + offline.html = спека (fidelity HIGH). Расхождения кода прототипа фиксируются решениями в досье; баги прототипа чинятся, не копируются; спорные продуктовые места — вопросами пользователю (§9). |

Палитра выведена совпадением контраста, а не инверсией: иначе проседают средние тона, и сильнее всех самый частый цвет приложения. Иконка лаунчера и цвета QR теме не следуют намеренно. |

## 4. Процесс разработки (handbook, уровень 2)

Досье `docs/tasks/BJ-N/`: `status.yaml`, `requirements.md`, `research.md`, `plan.md`, `decisions.md` (D-N), `open_questions.md` (Q-N с гейтами `pre_dev | pre_review | pre_testing`), `risks.md`, `contracts.md`. Профили `light | standard | full`, эскалация только вверх.

Фазы: research → **аппрув плана (человек)** → dev → review → test-planning → ручной прогон (человек) → **DONE (человек)**.

Сохранённые принципы handbook: стоп-правила дева (неясное требование / незадокументированное изменение контракта / миграция вне плана → стоп, возврат в research); ревью не верит handoff'у и перепроверяет по диффу; scope creep = провал ревью; вопросы блокируют только ту фазу, которую реально гейтят.

**Контракты проекта** (то, что переживает обновление приложения; изменение — только через `contracts.md` задачи):

1. Версия Dexie-схемы + миграции.
2. Схема экспортного JSON (versioned) + zip с фото; импорт старого экспорта в новую версию обязан работать.
3. Payload QR-рецепта (versioned).
4. Append-only реестры id: дескрипторы WHEEL (102), ключи TRAITS, ключи стадий (`bloom, pour, drain, steep, stir, press, valve, pause`) — на них ссылаются исторические записи журнала.
5. Схема записи `Grinder` в `packages/core` (общая с расширением).
6. Пиксельная сверка ключевых экранов с `offline.html`.

## 5. Приложение — стек и архитектура

React 18 + Vite + TypeScript strict, Dexie 4 (+`dexie-react-hooks` liveQuery), zustand (таймеру нужен стор вне React-дерева), Capacitor 6. Без роутер-библиотеки — nav-стек `screen + stack` как в прототипе; аппаратная «назад» Android — через Capacitor App plugin.

```
apps/journal/src/
  domain/    stages.ts, timer.ts, calibration.ts, freshness.ts, wheel.ts, colors.ts, devsvg.ts   ← чистые функции, юнит-тесты
  data/      wheel-dict.ts, traits.ts, strings/{ru,en}.ts, seeds.ts                              ← порт data.js
  db/        schema.ts (версии-миграции), repo/*
  platform/  camera, files, notify, keepawake, speech, share  — интерфейс + capacitor-реализация + web-фолбэк
  ui/        tokens.css, screens/*, components/*
```

Платформенный слой за интерфейсами = PWA-готовность: web-фолбэки (камера → file input, уведомления → no-op, голос → молчаливая деградация до клавиатуры — без баннеров, по handoff).

Порт `data.js`: tuple-типы (`readonly [id, ru, en]`), `Object.freeze`, `DESC` строится чистой функцией; ключи `STR` (145 RU/EN) — типизированный union; двойное enum-пространство `Entry.mode` (`perc|imm|hybrid|drip|cup`) не сводить к `TRAITS.flow`.

Капитальная переносимая логика прототипа (инвентаризована по `Brew Journal.dc.html`): `stagesFor` (5 веток: drip / perc / imm / hy-imm / hy-mid; компенсация округления воды последним проливом), таймер (пауза закрывает стадию фактической длительностью, «стекание» пишется отдельной стадией `pause`, маркеры нулевой длительности `stir`/`valve` «проглатываются» с записью в rec), калибровка (§2 D-1), devSvg (геометрия из признаков), колесо (3 уровня, oklch от категории, zoom-анимация, память = union дескрипторов done-записей), сравнение (строковый дифф 15 строк). Обвязка прототипа (`support.js`, `image-slot.js`, `ios-frame.jsx`) — не переносится (проверено: доменной логики там нет).

## 6. Модель данных (Dexie v1)

- `grinders` — свои кофемолки; хранятся как linear-запись, совместимая с типом `Grinder` ядра (`micronsPerStep`, `zeroOffsetMicrons`, `scale`); минимум одна.
- `beans` — `{id, form: beans|ground|drip, name?, roaster?, roast: ISO, photos: PhotoRef[], weight/left | count/leftCount + dose}`. **`photos` — массив** `{path, thumb}` (D-3: README wins), первое фото — лицо, порядок задаёт пользователь.
- `devices` — `{id, name, flow, bottom, wall, filter, material, vol}` (ключи TRAITS).
- `entries` — по модели handoff README §«Модель данных»; `stages` — фактические `[key, sec, water]` включая `pause`; `status: pending|done`; `desc: [descriptorId, intensity 1..3][]`.
- `settings` — `lang`, `calib {offset, src}`, `convFrom/convTo`, recents.

Фото: `Camera.getPhoto({quality: 80, width: 2048})` → файл в `Directory.Data`, миниатюра 256px (~15 КБ) в Dexie. Никакого base64 в БД. Экспорт: JSON + папка фото одним zip; импорт — обратная распаковка. Бюджет: < 200 МБ за годы (~40–50 МБ/год фото).

## 7. Известные расхождения прототипа (фиксируются как D-N в досье соответствующих задач)

Чиним/следуем README: краш сравнения на `cup`-записях (`bean: null`); `photos` число → массив; полноэкранный просмотр фото; пустые состояния (журнал/полка «приглашают заварить»); недостающая компенсация воды в drip-ветке `stagesFor` (сделать как в perc); дубль формулы конвертации → один модуль; баг `fmtT(119.6) = "1:00"`; несовпадение id `s3` vs `s3db`; захардкоженные `TODAY`, `zero: 300`/`dp: 1` новой молки, `dose: 12` новой дрип-пачки; порядок толщин стенок devSvg (README: керамика > металл > стекло > пластик; код: стекло > металл); светлота колеса за пределами заявленных 0.60–0.78; кнопка таймера «ГОТОВО» (код: «ЗАВЕРШИТЬ»); экспорт/импорт/QR/голос — в прототипе фиктивны, реализуем по-настоящему.

## 8. Конвертер (детали)

`packages/core.convert()` даёт `{microns, target(snapped), band{low,high}, warnings}`. Поверх: `applyCalib(result, offset)` — сдвиг center/lo/hi в шагах своей молки; подсказка калибровки — лучшая done-запись по сладости (`diag.balance`) с помолом. `short` для пикера — из `model`; знаки — из `scale.unit` (`mark` → 1 знак). Экранные элементы — по дизайну: диапазон 46px как главный результат, полоса-шкала, техстрока `клики · µm · µm/шаг`, ВЗЯТЬ В ЗАВАРИВАНИЕ переносит откалиброванный центр в сетап.

## 11. Definition of Done (из CLAUDE_CODE_TASK, приёмка BJ-7)

1. `npx cap run android` собирает и ставит APK.
2. В авиарежиме полный цикл: пачка фотографией → заварка с таймером и паузой → оценка (шкалы + колесо + заметка) → журнал → сравнение двух → экспорт JSON.
3. Удаление приложения + импорт JSON восстанавливает базу.
4. Экран таймера не гаснет; после заваривания — локальное уведомление.
5. Пиксельная сверка ключевых экранов с `offline.html`.
