## 3. Сервисы прототипной среды, которые нужно заменить своим стеком

Чтобы перенести поведение экранов из `Brew Journal.dc.html` (класс `Component`) в реальное приложение, нужно самостоятельно реализовать следующее (сейчас это даёт `support.js`):

- **Управляющие конструкции `sc-for` / `sc-if`** (`support.js:611-660`) → аналог `.map()`/условный рендер в целевом фреймворке.

- **Реестр компонентов и подписки на изменения** (`registry.ts`, `support.js:1591-1619`), **hot-reload/streaming** (плейсхолдеры-шиммеры для «догружаемого» контента, `support.js:86-131,1791-1815`) — механизм live-редактирования прототипа в дизайн-инструменте (Claude Design canvas), не имеет отношения к продакшн-приложению.
- **Загрузка React/ReactDOM/Babel с CDN во время выполнения** (`support.js:1143-1355`) — специфично для одностраничного HTML-прототипа без сборки; в реальном приложении будет обычный бандлер (Vite/webpack) и импорт зависимостей.
- **`x-import`/`dc-import`** — динамический импорт внешних JS/JSX-модулей и глобальных custom elements (в т.ч. как подключаются `image-slot.js` и `ios-frame.jsx` в сам прототип) — заменяется обычными `import`.

- **`postMessage`-мост с родительским фреймом хостящего дизайн-инструмента** (`__dc_theme`, `__dc_booted`, `__dc_design_mode`, `helmet.ts`, `support.js:1366-1419,1854-1893`) — целиком инфраструктура превью внутри Claude Design, никак не переносится.

  1. Условный рендер экрана/секций (`sc-if`) → компонентный роутинг/условный JSX.
  2. Списки записей/девайсов/дескрипторов (`sc-for`) → `.map()`.
  3. Состояние экрана (`this.state`, `this.setState`) → `useState`/стор.
  4. Побочные эффекты при монтировании/обновлении (`componentDidMount`/`componentDidUpdate` в `Component`, если используются) → `useEffect`.

Любая логика, вызываемая из шаблона через `this.method()` (`devSvg`, `colOf`, `hueOf`, `arcPath`, конвертация и т.д.) — она физически находится в `class Component` внутри `Brew Journal.dc.html`, а НЕ в проверяемых трёх файлах; это и есть то, что реально нужно портировать по функционалу (переписать под целевой фреймворк), просто оно живёт не в `support.js`.

## 4. `image-slot.js` — что делает с изображениями и чему может научить

- **Не хранилище приложения**, а инструмент дизайн-прототипирования: слот — заглушка изображения (`placeholder`), которую можно заполнить drag&drop или кликом «browse files» (`image-slot.js:439-529, 571-596`).
- **Пайплайн загрузки**: `File` → `createImageBitmap` → рисование в `<canvas>` с уменьшением до `MAX_DIM=1200` (и до 2× ширины рендер-контейнера) → кодирование в WebP `q=0.85` через `canvas.toDataURL('image/webp', 0.85)` (`image-slot.js:259-273`). Итоговое изображение хранится как **base64 data-URL** в объекте `{u, s, x, y}` (`s`=scale, `x/y`=смещение кропа) — `image-slot.js:236-252,912`.
- **Персистентность** — не файловая система реального приложения, а сайдкар `*.state.json` рядом с HTML-файлом прототипа, читаемый через `fetch()` и записываемый через `window.omelette.writeFile` (существует только внутри среды дизайн-инструмента, `image-slot.js:158-230`). Вне этой среды (`window.omelette` отсутствует) слот **read-only** (`image-slot.js:1088-1090`, `editable = !!(window.omelette && window.omelette.writeFile)`).
- **Реframe (кроп/зум)**: drag для панорамирования, drag за угловые «ручки» для масштабирования с фиксацией противоположного угла, `wheel` для зума к курсору, `Escape`/клик снаружи — коммит (`image-slot.js:624-702, 747-831`). Ограничение масштаба `clampS` 1..5 (`image-slot.js:232-233`).
- **Валидация типов**: только `image/png|jpeg|webp|avif` (`ACCEPT`, `image-slot.js:156`), SVG/GIF намеренно исключены (SVG может нести скрипт; GIF теряет анимацию при re-encode через canvas) — с комментарием-обоснованием.
- **Атрибуция Unsplash** (обязательные `credit`/`credit-href`, UTM-параметры, error-tile при отсутствии атрибуции, `image-slot.js:96-148,1120-1218`) — юридическое требование дизайн-инструмента для стоковых фото, полностью нерелевантно приложению, где пользователь фотографирует свою пачку кофе.

**Что реальный фото-пайплайн приложения МОЖЕТ позаимствовать (по идее, не по коду)**:
- Паттерн «resize+recompress через canvas перед сохранением» (ограничение долгой стороны, WebP, качество ~0.85) — разумный подход и для фото пачек кофе (README требует «фото столбцом», «минимум два снимка»), чтобы не раздувать локальное хранилище (IndexedDB).
- Хранение кропа как `{s,x,y}` относительно исходного изображения, а не перезапись пикселей — позволяет менять рамку без потери оригинала; для карточки пачки (118px квадрат) такой подход тоже уместен.
- Разграничение «типов файлов» (raster only, без SVG/GIF) как модель валидации аплоада.
- НО: сам код (custom element, сайдкар-JSON, `window.omelette`, Unsplash-атрибуция, drag-reframe с popover/top-layer API) — специфичен для дизайн-инструмента и **не переносится**, только паттерн «downscale в canvas перед сохранением» достоин повторного использования как идея.

## 5. `ios-frame.jsx` — что предоставляет рамка телефона

Это **чисто визуальный муляж** (bezel/статус-бар/клавиатура) для показа прототипа "как на экране iPhone" внутри дизайн-инструмента — не иметь отношения к реальной раскладке приложения на устройстве:
- **Размеры рамки по умолчанию**: `width=402, height=874` (`ios-frame.jsx:203`) — это логические CSS-пиксели контента, примерно соответствующие iPhone 14/15 Pro (безопасная область экрана), но это ЗНАЧЕНИЯ ПО УМОЛЧАНИЮ ФРЕЙМА, не безопасные отступы приложения как таковые.
- **Статус-бар**: `padding: '21px 24px 19px'` сверху для времени/иконок (`ios-frame.jsx:24-28`) — жёстко зашитая высота под статус-бар iOS, НЕ передаётся как настраиваемая safe-area-переменная.
- **Nav bar**: `paddingTop: 62` (учитывает высоту статус-бара + отступ) (`ios-frame.jsx:109`).
- **Home indicator**: абсолютно спозиционированная полоса высотой 34px снизу (`ios-frame.jsx:232-241`) — это визуальная имитация нижней safe-area (home indicator), а не программный `env(safe-area-inset-bottom)`.
- **Клавиатура** — опциональный блок `IOSKeyboard`, целиком отрисованный вручную (не системная), с раскладкой QWERTY (`ios-frame.jsx:249-348`).
- Никаких реальных CSS env()-safe-area переменных, никакого JS API для получения границ вьюпорта устройства — всё это статичные px-константы для демонстрации в браузере.

**Вывод по layout-константам**: README (`README.md:103`) отдельно указывает "safe area сверху и снизу" как требование к реализации — но сама эта константа/логика в `ios-frame.jsx` не formalизована как переиспользуемый токен (нет экспортируемых `SAFE_AREA_TOP`/`SAFE_AREA_BOTTOM`), это просто хардкод внутри разметки конкретных React-компонентов рамки. Разработчику реального приложения нужно использовать нативные safe-area примитивы платформы/Capacitor (`env(safe-area-inset-*)`), а не переносить эти пиксельные значения из `ios-frame.jsx`. Единственное, что можно взять как ориентир — сами числа (высота статус-бара ~62px «сверху под контент», ~34px снизу под home indicator) как визуальную референс-подсказку при вёрстке, но не как программные константы для переноса.

Файл не используется для реальной верстки экранов Brew Journal (те верстаются напрямую в шаблоне `.dc.html`) — `IOSDevice` лишь оборачивает готовый экран рамкой при просмотре прототипа в браузере (виден переключатель размеров/тем в `Brew Journal offline.html`, но сам компонент не содержит логики экранов).

## 6. Вердикт

**Да, безопасно игнорировать все три файла (`support.js`, `image-slot.js`, `ios-frame.jsx`) при переносе кода — claim README подтверждён.** Доменной логики (конвертация помола, цвета/геометрия колеса вкусов, SVG-чертёж девайсов, стадии заваривания/таймер, модели данных, строки i18n) в них нет; всё это действительно сосредоточено в `data.js` (чистые функции/словари/сиды: `toUm`/`fromUm`/`convert` — `data.js:35-37`, `WHEEL`/`DESC` — `data.js:50,97`, `catColor` — `data.js:99`, `TRAITS`/`GRINDER_DB` — `data.js:8,102`, `STR` — `data.js:158`) и в `class Component extends DCLogic` внутри `Brew Journal.dc.html` (`devSvg()` — `:1099`, `hueOf`/`colOf`/`arcPath` — `:963,1074,1095` и вся остальная логика экранов/таймера/стадий).

**Оговорки**:
1. **`support.js` объясняет синтаксис**, в котором написан `Brew Journal.dc.html` (`{{ }}`-интерполяция, `sc-for`/`sc-if`, `this.setState`/`this.state`/`renderVals()` из `DCLogic`). Сам файл переносить не нужно, но при чтении/переписывании `class Component` полезно понимать эту семантику (см. чеклист в разделе 3) — иначе легко неверно интерпретировать шаблонные конструкции как «настоящий» JS-код.
2. **`image-slot.js`** можно use как источник *идеи* (canvas-downscale в WebP перед сохранением, хранение кропа отдельно от байтов изображения) для фото-пайплайна «полки» — но не как код: механизм хранения (`window.omelette.writeFile`, сайдкар-JSON), Unsplash-атрибуция, custom element с popover/top-layer API — специфика дизайн-инструмента и не имеет отношения к IndexedDB/Capacitor-камере реального приложения.
3. **`ios-frame.jsx`** можно использовать как визуальный ориентир пиксельных размеров safe-area (константы `21/19px` статус-бар, `62px` под nav bar, `34px`/`139×5px` home indicator), но это не формализованные токены — их нужно заменить на нативные `env(safe-area-inset-*)`/Capacitor API, а не копировать числа как есть.
4. Проверка ограничена тремя названными файлами; `Brew Journal offline.html` (single-file эталон) и сам `Brew Journal.dc.html` целиком не были предметом данной проверки (только выборочный grep для перекрёстной сверки) — если потребуется полный аудит `class Component`, это отдельная задача.
